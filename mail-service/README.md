# Почтовый сервис демонстрации 2FA

Маленький сервис, который отправляет письмо с кодом подтверждения для
раздела «Попробуйте руками» на сайте «ИБ-Гид».

Сайт собирается статикой и лежит на GitHub Pages — отправлять оттуда
письма нечем. Сервис живёт отдельно, на собственном хостинге, а сайт
ходит к нему по HTTPS.

## Что он делает и чего не делает

Принимает `{ email, code }` и кладёт письмо в почту.

Код придумывает **браузер**, и он же виден на экране. Это осознанно:
демонстрация показывает, как выглядит подтверждение по почте, а не
настоящая двухфакторная защита. Настоящая система держит код в тайне от
того, кто его вводит. Поэтому здесь нет хранилища, срока жизни и сверки —
добавлять их незачем: как только код перестаёт быть виден, половина
демонстрации теряет смысл.

## Почему без Brevo и без Vercel

Серверные функции на Vercel не открывают исходящие соединения: SMTP-порт
закрыт, установить TLS внутри функции нельзя. А почтовый агрегатор
Brevo требует подтверждения телефона, чтобы выдать ключ.

Собственный хостинг обеих проблем не имеет: исходящие на порт 587
проверены и открыты, `npm install` выполняется при старте. Поэтому
отправка идёт напрямую через nodemailer.

## Пароль приложения

Gmail и Яндекс не принимают основной пароль ящика по SMTP — только
специальный. Порядок одинаковый:

1. Включить двухэтапную аутентификацию в аккаунте Google или Яндекса.
2. В настройках безопасности найти «Пароли приложений» и выпустить его
   для почты.
3. Полученные 16 знаков положить в `SMTP_PASS`.

Без этого шага вход невозможен, и ошибка выглядит как «неверный логин».

## Настройка сервера

1. Положить в корень сервера файл `index.js`.
2. Задать переменные окружения — одним из двух способов:

   **Через файл `.env`** — в панели: Configuration → Environment.
   Панель записывает файл на сервер, сервис читает его сам при старте.
   Именно этот способ и он надёжнее: встроенная поддержка `.env`
   появилась в Node только с версии 20.6, а на сервере стоит 19.9, и на
   `--env-file` рассчитывать нельзя.

   **Через Startup Variables** — на странице Startup. Переменные попадут
   в процесс напрямую и имеют приоритет над файлом `.env`.

   | Имя | Значение |
   |---|---|
   | `SMTP_HOST` | `smtp.gmail.com` или `smtp.yandex.ru` |
   | `SMTP_PORT` | `587` |
   | `SMTP_SECURE` | `false` для 587, `true` для 465 |
   | `SMTP_USER` | адрес ящика-отправителя |
   | `SMTP_PASS` | пароль приложения |
   | `MAIL_FROM` | что писать в поле «От» |
   | `ALLOWED_ORIGIN` | `https://normalguy123412-design.github.io` |
   | `PORT` | назначенный панелью порт, по умолчанию `11678` |

3. Перезапустить сервер — переменные читаются только при старте.
4. Если файл `package.json` не кладёте, впишите в Startup Variables
   строку `NODE_PACKAGES=nodemailer`: панель выполнит установку сама.

Приложение слушает `0.0.0.0`, а не `127.0.0.1`: панель об этом
предупреждает, и при привязке к локальному адресу поддомен покажет
пустоту.

## Проверка со своей машины

`check-send.cjs` отправляет одно настоящее письмо и печатает ответ
почтового сервера дословно. Ни сервер, ни панель для этого не нужны.

```bash
cd mail-service
npm install
# создать .env рядом с этим скриптом — по образцу .env.example
node check-send.cjs ваш@ящик
```

Он печатает, сколько знаков в пароле, — это сразу выдаёт обрезанный или
перепутанный пароль приложения: у Google он всегда ровно 16.

Ответ сервера разбирается на человеческий язык:

| Что ответил сервер | Что делать |
|---|---|
| `535 BadCredentials` | основной пароль вместо пароля приложения |
| `550 User unknown` | опечатка в адресе |
| `ECONNREFUSED` | закрыт порт, обычно 25 |
| `530` требует шифрование | проверьте, что порт 587 |

Зачем это отдельно от страницы проверки: так отвечается на вопрос
«работает ли мой пароль» — самая частая причина молчаливого отказа, и на
сервере её не отличить от «сервер настроен неверно». Страница эту
подробность прячет: посетителю она не нужна, а при настройке — очень.

## Проверка со страницы

Чтобы не набирать команды, у сервиса есть страница отправки:

```
https://site.wisp.uno/?key=<токен>
```

Токен придумывает сам сервис при старте и печатает в консоль — ссылка с
ним тоже там, в логе. Если задать `TEST_TOKEN` в настройках, он будет
постоянным.

На странице есть поле «кому отправить»: писать можно на любой адрес, а
по умолчанию подставляется `TEST_TO`. После отправки показывается тот же
код, что ушёл в письме, — сверьте их, так проверяется вся цепочка от
нажатия до входящих.

Почему страница закрыта токеном: писать можно на любой адрес, и без
замка такая форма стала бы почтовым шлюзом — ею пользовался бы любой,
кто узнает адрес сервера. Заглушка 404 выбрана вместо 403 потому, что
разница кодов сказала бы посетителю, что страница есть и просто закрыта.

Ограничение частоты здесь то же, что и у основного эндпоинта: 10 писем
в час с одного адреса и 3 на один ящик. Проверка не должна быть обходным
путём мимо счётчиков.

## Локальная проверка

```powershell
cd путь\до\проекта\mail-service
npm install
node index.js
```

Самый быстрый способ — положить рядом `.env` с теми же значениями и
запустить без единой команды: сервис прочитает файл сам. Файл `.env`
закрыт в `.gitignore` и в репозиторий не попадает.

## Проверка

```bash
# жив ли сервис
curl https://<поддомен>/health

# уходит ли письмо
curl -X POST https://<поддомен>/api/send-code \
  -H "Content-Type: application/json" \
  -H "Origin: https://normalguy123412-design.github.io" \
  -d '{"email":"ваша@почта","code":"123456"}'
```

Что означают ответы:

| Ответ | Что это значит |
|---|---|
| `{"ok":true}` | письмо ушло |
| 403 | не совпал `ALLOWED_ORIGIN` — сервис работает, но не для этого сайта |
| 429 | сработало ограничение частоты |
| 502 | почтовый сервер отказал; смотреть лог сервиса |
| 502 + в логе «Не заданы переменные» | сервис стартовал без настроек и сразу остановился |

## Проверка связи: скрипт check-smtp.cjs

Отдельный скрипт, который смотрит, дойдёт ли письмо вообще. Ничего не
настраивает и ничего не отправляет — только проверяет связь.

Запускать надо **на том самом узле, где будет жить сервис**. Ответ
зависит от сети: с домашнего компьютера порт открыт, с сервера может
быть закрыт, и наоборот.

```bash
node check-smtp.cjs
node check-smtp.cjs --verbose        # сырые ответы серверов
node check-smtp.cjs --host smtp.gmail.com --port 587
```

Расширение `.cjs` и `require` вместо `import` — не случайность: панель
запускает файл как CommonJS, потому что рядом нет `package.json`, и код
на `import` там падает с `SyntaxError`. Имя `.cjs` работает всегда.

Что он проверяет и как читать ответ:

| Ответ | Что означает |
|---|---|
| `ДОСТУПЕН` + `ОТКРЫТ` | почта заработает |
| `ДОСТУПЕН`, но `ЗАКРЫТ` | хост режет исходящие на почтовые порты |
| `НЕТ DNS` | исходящего DNS нет, SMTP не заработает ни при каких настройках |
| `ОТКРЫТ, ЖДЁТ TLS` | порт 465 — это норма, он требует шифрования сразу |
| `ОТВЕЧАЕТ НЕ ПОЧТА` | порт открыт, но там не почтовый сервер |

Отдельная тонкость: Gmail и Mail.ru не показывают `AUTH` в баннере.
Это не поломка — они объявляют его только после `STARTTLS`. Скрипт
об этом предупреждает, иначе легко сделать вывод, что сервер не годится.

## Ограничение частоты

Эндпоинт публичный, и без счётчиков любой мог бы слать через него
письма от вашего имени. Счётчики есть: 10 писем в час с одного адреса и
3 — на один адрес получателя. Второй важнее: без него через сайт можно
завалить почту конкретному человеку.

Счётчики живут в памяти процесса и сбрасываются при перезапуске сервера.
Для школьной защиты этого достаточно: полноценная защита от злоупотреблений
жила бы на стороне почтового провайдера.

## Что попадёт в репозиторий, а что нет

`.env`, `node_modules` и служебные файлы закрыты в `.gitignore` и в git
не попадают — проверено `git add --dry-run`. В репозиторий уходит
только `.env.example`, где перечислены имена переменных и заглушки.
